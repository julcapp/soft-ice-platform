# Единый порядок разработки

## Основной принцип

Одна задача — одна ветка — один Pull Request.

Телефон и ПК являются только рабочими устройствами. Они не создают отдельные ветки
для одной задачи. GitHub остаётся единственным источником исходного кода.

## Ветки

- `main` — стабильная принятая версия;
- `integration/unified-v0.36.0` — единая проверяемая версия следующего релиза;
- `feature/<задача>` — новая функция;
- `fix/<задача>` — исправление;
- `docs/<задача>` — самостоятельное изменение документации;
- `hotfix/<задача>` — отдельно согласованное срочное исправление.

Новые ветки `work/phone/*` и `work/pc/*` не создаются. Существующие legacy-ветки
можно только завершить или закрыть после проверки.

Запрещено напрямую отправлять изменения в `main` и `integration/*`.

## Начало задачи

1. Выполнить `git fetch origin --prune`.
2. Убедиться, что рабочее дерево чистое.
3. Создать одну ветку задачи от актуальной `origin/integration/unified-v0.36.0`.
4. Зафиксировать цель и границы изменения.

## Переход между телефоном и ПК

1. Завершить текущий логический блок и отправить коммиты в GitHub.
2. На втором устройстве выполнить `git fetch origin --prune`.
3. Переключиться на ту же удалённую ветку задачи.
4. Проверить точное совпадение head-коммита и только затем продолжить.

Создавать новую ветку той же задачи на другом устройстве запрещено. Если две версии
уже появились, работа останавливается: сравниваются изменения, выбирается одна
каноническая ветка, конфликты разрешаются осознанно и тесты выполняются повторно.

## Pull Request

Pull Request создаётся из ветки задачи в `integration/unified-v0.36.0`.

Обязательны:

- отсутствие конфликтов и незапланированных файлов;
- отсутствие секретов и открытых персональных идентификаторов;
- целевые тесты изменённого модуля;
- полный применимый backend/UI-набор;
- проверка Prisma schema и чистой цепочки миграций при изменении данных;
- сборка изменённых frontend-приложений;
- описание влияния на API, данные, роли и интерфейсы;
- обновление changelog, сценариев и архитектурных решений;
- подтверждение, что продакшен не изменён.

PR объединяется только после зелёных обязательных проверок и точной проверки head SHA.

## Развёртывание

1. Feature/fix/docs-ветки не развёртываются в production.
2. Изменение сначала входит в интеграционную ветку.
3. Выполняются тестовая миграция, сквозная приёмка и проверка отката.
4. Создаётся версия релиза и резервная копия.
5. Переключение production выполняется только после отдельного решения.
6. После переключения проверяются локальный и внешний `/health`.
7. При ошибке выполняется откат на предыдущую проверенную версию.
