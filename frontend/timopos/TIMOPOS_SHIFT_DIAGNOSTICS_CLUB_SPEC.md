# TimoPOS 2.0 — смены, расписания, оборудование, клуб (утверждённые требования 14.11.2026)

## 1. Время работы торговой точки
- Расписание задаёт администратор для **каждой** точки. Пример: 08:00–18:00 по локальному часовому поясу торговой точки.
- Хранить IANA timeZone и интервалы по дням недели; выходные и исключения/праздники задавать отдельно, время берётся **с сервера**, не из часов терминала.
- **Круглосуточная точка:** отдельная настройка `mode: 24_7`, работа 00:00–24:00 без дневного перерыва. Поля `00:00–00:01` означают **одну минуту**, а не сутки; в админке предоставить явный переключатель «Круглосуточно». Для обычных точек `mode: SCHEDULED`.
- Круглосуточность не означает автоматическую продажу: даже в 00:00 нужен подтверждённый MAX-вход продавца и открытая им смена.
- Раньше 08:00 продавец вправе пройти MAX-авторизацию, просматривать разрешённые сведения и результаты самодиагностики, но не вправе открыть смену, оплатить, создать продажу или выдать продукцию. После 18:00 запрет продажи/выдачи действует автоматически, даже если смена осталась открытой.
- Покупатель не может инициировать выдачу в обход серверного графика через TimoPOS.
- При отсутствии, некорректности или противоречивости расписания продажи запрещены. Событие логировать.

## 2. Авторизация через MAX и коды
- Точка знает свой terminalId и pointId из защищённой конфигурации backend.
- Телефон вводится на заблокированном терминале. Backend сверяет OrganizationMember.status, роль SELLER, назначение точки и verified MAX identity.
- Каждая попытка запроса входа порождает **новый шестизначный OTP, гарантированно отличный от непосредственно предыдущего кода** для того же сотрудника и терминала. Генерировать криптографически, сверять HMAC отпечаток нового кода с предыдущим перед отправкой; старый код инвалидировать атомарно. Ранее выданные неиспользованные коды становятся недействительными. TTL 5 минут; не более 5 ошибочных вводов, ограничения частоты/пересылки.
- Доставлять в *личный* чат основного MAX-бота «Клуб У Тимоши» только для номера, ранее доказанно привязанного владельцем. При неверном номере не разглашать существование учётной записи.
- После успешной проверки загрузить с backend ФИО, **маскированный телефон**, точку и состояние смены. Данные клиента не загружать.
- Нужно учесть случай повторного запроса на код после задержки отправки (sender и repo должны согласовать порядок, не оставляя старый код действительным).

## 3. Открытие и закрытие смены
- **Первая основная кнопка после авторизации: «Начать смену»**. Продавец **лично нажимает** её на экране: автоматическое начало смены по графику или при MAX-входе запрещено. Для открытой смены доступна «Закончить смену». Начать смену возможно только по графику.
- Открытие: атомарно создать смену с sellerId, pointId, terminalId, startedAt, начальным кассовым состоянием и audit event. Запрет двух пересекающихся смен для одного терминала.
- Статусы: CLOSED/OPEN; закрытие фиксирует endedAt, итог выручки, оплат, возвратов, выдач и отказов. Учёт рабочего времени продавца вести по паре времени `startedAt / closedAt`, с серверным audit trail и раздельным учётом перерывов при будущей необходимости.
- **Нажатие «Закончить смену» — атомарная серверная транзакция:** фиксировать закрытие смены и **сразу отзывать серверную сессию продавца**. Админпанель должна немедленно показывать закрытую смену и разорванную сессию. Повторная продажа невозможна без новой MAX-авторизации и нового физического нажатия «Начать смену».
- После подтверждённого закрытия смены показывать итоги **30 секунд** и затем блокировать экран. Это лишь UI-отсрочка: доступ на backend прекращён **сразу**, пока идёт отсчёт. Если backend недоступен и закрытие не подтверждено — не показывать успешное закрытие.
- «Заблокировать» (без окончания смены) скрывает UI и отзывает/приостанавливает авторизацию до повторной MAX-проверки; действующая бизнес-смена может остаться открыта.
- Отсутствие связи во время закрытия: не показывать ложный успех. Серверный факт закрытия, а не localStorage, является источником истины.

## 4. Технологическое меню и стартовая диагностика
- Техменю доступно из блокировки в режиме **только диагностического просмотра** либо в рабочем интерфейсе с правами техника/администратора для опасных действий; обычный продавец не может исполнять тестовую выдачу/калибровку.
- На старте терминала — опрос зарегистрированного оборудования, драйверов и интеграций через локальный агент оборудования; список устройств формируется из конфигурации точки, а не из любого устройства ОС.
- Проверить: дисплей/тачскрин (если есть датчики/драйверы), QR/штрихкод-сканер, чековый принтер (подключение, бумага, ошибка, крышка), кофемашина и фризер (состояние/ошибка/готовность), связь с backend, канал MAX (как серверная проверка), платёжный провайдер, фискализацию, сеть/DNS/TLS, задержку/доступность канала и примерную скорость (при наличии безопасного тестового endpoint).
- Статусы: OK / ПРЕДУПРЕЖДЕНИЕ / КРИТИЧЕСКАЯ ОШИБКА / НЕ НАСТРОЕНО / НЕТ ОТВЕТА. Показать имя устройства, обязательность, время последнего ответа, описание, действие для оператора.
- Не считать устройство ОК только потому, что его драйвер найден: использовать heartbeat/статус периферии. Не выдавать «всё OK», если связь с диагностическим агентом отсутствует.
- При отказе некритичного устройства допускаются только операции, не требующие этого устройства. Пример: принтер без бумаги — предупреждение, но продажи допустимы **лишь если способ фискализации и предоставления чека правомерно работает без печати**. Кофемашина неисправна — блокировать кофе, не обязательно мороженое. Нет подтверждённой оплаты или backend — блокировать оплату и выдачу всех товаров.
- Интерфейс показывает текущий состав/технические характеристики: модель, серийный номер (по роли), прошивки, версия агента, драйвер, интерфейс USB/COM/Network/Bluetooth, состояние и обновления.

## 5. «Клуб Тимоши» на терминале
- **Никаких общих списков клиентов, ФИО, email и телефонов продавцу не показывать.**
- Клиент **сам диктует номер**. Продавец вводит его в поисковое поле. Сервер проверяет актуальную точку, роль, рабочую сессию, rate limit и журналирует обоснованный поиск.
- Если клиент найден и подтверждён: экран только «Участник клуба» и **доступный бонусный баланс**, без ФИО и номера в ответе. Списания бонусов — только по правилам программы и с подтверждением клиента (дополнительное подтверждение при необходимости); один телефон не даёт права списывать чужие бонусы.
- Если клиент отсутствует: «Пригласить в клуб?» → **«Вступить» / «Отказаться»**. Для «Вступить»: покупатель выбирает **MAX или Telegram**. Терминал создаёт одноразовый запрос/deep link для бота, но **не создаёт подтверждённый профиль сразу** и не отправляет спам на произвольный телефон.
- Бот просит покупателя подтвердить владение номером через request_contact, затем представляет политику ПДн и запрашивает отдельное обязательное согласие. Рекламное согласие — независимое и необязательное. Только после подтверждения номера и согласия backend завершает регистрацию и фиксирует тип, версию, время, канал и ID согласия.
- Если отказался — не создавать клиентский аккаунт, не сохранять номер в журнале, не блокировать разовую покупку. При желании допускается гостевая покупка без клуба.
- Уже существующий TerminalChannelChallengeService — канал подтверждения владельца контакта; архитектура требует адаптации для сценария TimoPOS без смешивания с SellerMaxAuthService.
- Не допускать перебора телефонных номеров (поисковый оракул); защита от массовой проверки membership с rate limiting и минимизацией ответа. На неавторизованном терминале никакой поиск по телефону не доступен.

## 6. Неизменяемые требования
- Основной сервер 78.140.15.84; 91.186.217.13 — Telegram-канал.
- Домен app.utimoshi.ru сохранить без redirect.
- Не менять работающий MAX-бот «Soft_ICE Безопасность».
- Оплата через ЮKassa/СБП проверяется сервером, выдача только при SUCCEEDED и разрешении точки/смены/часов.
- Все изменения только в отдельной ветке до интеграционных тестов и одобрения релиза на production.

## 7. Приёмочные тесты
1. 07:59:59 — вход/просмотр доступен, смена/продажа/выдача запрещены.
2. 08:00:00 — начало смены возможно, только после него разрешена продажа.
3. 17:59:59 — продажа разрешена; 18:00:00 — запрет независимо от состояния shift.
4. Смена закрыта: итог 30 сек, затем обязательная блокировка и отзыв сессии; обратный счёт не подменяет backend.
5. Повторное получение MAX-кода отменяет старый; код действителен 5 мин и не может использоваться второй раз.
6. Неисправный принтер с бумагой/без бумаги, сканер отключён, кофемашина недоступна, backend offline: корректное разграничение warning/critical и товаров.
7. Не настроенные устройства обозначены «не настроено», отсутствующие ожидаемые — как ошибки, no false success.
8. Продавец может искать только конкретный диктуемый телефон, не может перечислить клиентскую базу.
9. На найденного клиента — только членство и бонусы, без ПДн; при отсутствии — «Вступить/Отказаться».
10. Запрос регистрации через MAX/Telegram требует подтверждение своего контакта и отдельное обязательное согласие на ПДн; отказ разрешает гостевую покупку.


## 8. Календарь работы точки — дополнение
- «Круглосуточно» означает непрерывно каждый день с понедельника по воскресенье, включая полночь; mode=24_7 и IANA часовой пояс точки.
- Для режима SCHEDULED администратор отдельно задаёт часы будней (понедельник–пятница), субботы и воскресенья. Пустой интервал означает выходной. Для каждого дня можно создать несколько временных интервалов.
- Пример: будни 08:00–18:00, суббота 10:00–16:00, воскресенье выходной. Контроль графика — серверным временем точки.
- Режим 24/7 не отменяет MAX-вход сотрудника, личное нажатие «Начать смену» и немедленный запрет продаж при закрытии смены.
- Смены круглосуточных точек могут пересекать полночь; в БД UTC timestamps, в отчётах часовой пояс точки и реальная продолжительность.

## 9. Синхронизация времени
- Источник истины при начале/закрытии смен, продажах и выдаче — серверное время основного сервера 78.140.15.84. Браузерные часы не авторизуют операции.
- При запуске, после восстановления связи, после перезапуска устройства и каждые 2 часа (7200000 мс) терминальный агент сверяет время с доверенным HTTPS endpoint backend.
- HTTP endpoint возвращает UTC epoch milliseconds с Cache-Control: no-store, требует доверенного TLS и авторизации устройства. Агент сравнивает серверное и локальное время с учётом RTT и измеряет clock skew.
- В технологическом меню отображать локальное время в часовом поясе точки, серверное время, отклонение, RTT, дату последней успешной сверки, время следующей и статус: OK / ПРЕДУПРЕЖДЕНИЕ / КРИТИЧЕСКОЕ / НЕ ПРОВЕРЕНО.
- Для диагностического прототипа: <=2 секунд OK; >2 секунд WARNING; >30 секунд CRITICAL; превышение интервала 2 часа — STALE. Пороги утверждаются после реальных замеров.
- Сам веб-интерфейс не может исправлять системные часы. При отклонении локальный системный агент должен обращаться к NTP/chrony/Windows Time через ограниченные права. Не устанавливать системное время из неподтверждённого API-ответа.
- При отсутствии соединения с backend продажи запрещены; при неизвестном времени не выдавать ложный OK. Сервер на каждой финансовой операции самостоятельно проверяет расписание и смену.
- TimoPosClockPolicy.js проверяет только логику диагностики; фактический 2-часовой scheduler, endpoint, OS/NTP коррекция и приборная проверка ещё не интегрированы.


## 10. Технологические перерывы — дополнение 14.11.2026

- Доступны две отдельные кнопки в открытой смене: **«Начать перерыв»** и, после подтверждённого начала, **«Закончить перерыв»**. Продавец нажимает их лично, как и управление сменой. Никакой автоматической фиксации «отсутствовал» по факту бездействия.
- Перерыв НЕ закрывает смену и НЕ отзывает авторизацию MAX. Статус смены остаётся OPEN, а её текущий режим становится BREAK_ACTIVE. Записываются sellerId, pointId, terminalId, shiftId, startedAt и endedAt по серверным UTC timestamp.
- Как только backend подтверждает начало, **новые продажи, новые оплаты, выдача из TimoPOS и списание бонусов запрещены** независимо от часов работы; просмотр и технологическая диагностика разрешены. Клиентские операции должны проверять статус перерыва **на сервере** непосредственно перед финансовым/физическим действием, а не доверять браузеру.
- Уже оплаченные и начатые операции не следует безусловно бросать: перед началом перерыва завершить находящиеся в критической фазе заказы или инициировать согласованную безопасную эскалацию/возврат; не выполнять повторную выдачу. Принятие новых заказов блокируется сразу.
- Нельзя начинать второй активный перерыв; нельзя завершать чужой перерыв или перерыв закрытой смены; все изменения фиксируются в аудите с причиной TECHNICAL. На сервере требуется атомарность и уникальный индекс на один активный перерыв смены.
- После подтверждённого окончания перерыва продажи возвращаются **только если** смена по-прежнему OPEN, MAX-сессия актуальна, график работы точки допускает продажи, оборудование/фискализация/связь исправны. Само окончание перерыва не обходит эти ограничения.
- При завершении смены с незакрытым перерывом серверная транзакция автоматически завершает активный перерыв временем closedAt, закрывает смену и отзывает сессии. Время перерыва не может выходить за границы смены; пересечения запрещены.
- Для отчётов админпанели хранить отдельные события каждого перерыва. Показатели: полная длительность смены, суммарное время технологических перерывов, **время работы без перерывов**, число перерывов; по отдельному показателю — периоды без продаж. Перерыв является самоотметкой сотрудника, но не подтверждает фактическое физическое отсутствие. Отсутствие продаж не означает отсутствие продавца.
- Для круглосуточных точек перерыв может пересекать полночь. Все расчёты по UTC и часовому поясу точки. Корректность времени зависит от серверных часов и фоновой синхронизации раз в два часа.
- Сбой сети: нельзя показывать успешное начало или конец перерыва без серверного подтверждения; при недоступном backend новые операции невозможны.
- Реализация в рабочей ветке: TimoPosBreakService.js, серверная политика deny TECHNICAL_BREAK_ACTIVE, тесты и модели TimoPosShift/TimoPosTechnicalBreak. **Операционный repository с транзакциями, API, интерфейс админпанели и production пока не подключены.**

### Приёмочные проверки перерывов
1. MAX-вход + открытая смена + разрешённые часы → нажатие «Начать перерыв» → серверный статус ACTIVE → запрет продажи и выдачи.
2. «Закончить перерыв» → серверный статус ENDED → продажа доступна только при прочих выполненных условиях.
3. Двойное начало, чужой сотрудник или терминал, отозванная сессия → отказ.
4. Закрытие смены при активном перерыве → транзакционно завершить перерыв и закрыть смену, отозвать сессию.
5. Отчёт за смену 8 часов с перерывами 15+10 минут → 8 ч всего, 25 мин перерывы, 7 ч 35 мин работы без перерывов.
6. Отдельно показывать время без операций, не приравнивая его к физическому отсутствию.
