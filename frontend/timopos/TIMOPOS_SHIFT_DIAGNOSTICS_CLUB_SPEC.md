# TimoPOS 2.0 — смены, расписания, оборудование, клуб (утверждённые требования 14.11.2026)

## 1. Время работы торговой точки
- Расписание задаёт администратор для **каждой** точки. Пример: 08:00–18:00 по локальному часовому поясу торговой точки.
- Хранить IANA timeZone и интервалы по дням недели; выходные и исключения/праздники задавать отдельно, время берётся **с сервера**, не из часов терминала.
- Раньше 08:00 продавец вправе пройти MAX-авторизацию, просматривать разрешённые сведения и результаты самодиагностики, но не вправе открыть смену, оплатить, создать продажу или выдать продукцию. После 18:00 запрет продажи/выдачи действует автоматически, даже если смена осталась открытой.
- Покупатель не может инициировать выдачу в обход серверного графика через TimoPOS.
- При отсутствии, некорректности или противоречивости расписания продажи запрещены. Событие логировать.

## 2. Авторизация через MAX и коды
- Точка знает свой terminalId и pointId из защищённой конфигурации backend.
- Телефон вводится на заблокированном терминале. Backend сверяет OrganizationMember.status, роль SELLER, назначение точки и verified MAX identity.
- Каждая попытка запроса входа порождает **новый криптографически случайный шестизначный OTP** (совпадение чисел вероятностно возможно; если требуется гарантированное отличие от предыдущего, хранить last-code fingerprint и генерировать повторно до отличия). Ранее выданные неиспользованные коды становятся недействительными. TTL 5 минут; не более 5 ошибочных вводов, ограничения частоты/пересылки.
- Доставлять в *личный* чат основного MAX-бота «Клуб У Тимоши» только для номера, ранее доказанно привязанного владельцем. При неверном номере не разглашать существование учётной записи.
- После успешной проверки загрузить с backend ФИО, **маскированный телефон**, точку и состояние смены. Данные клиента не загружать.
- Нужно учесть случай повторного запроса на код после задержки отправки (sender и repo должны согласовать порядок, не оставляя старый код действительным).

## 3. Открытие и закрытие смены
- **Первая основная кнопка после авторизации: «Начать смену»** (или «Закончить смену» если активная смена уже есть). Она активна только по расписанию.
- Открытие: атомарно создать смену с sellerId, pointId, terminalId, startedAt, начальным кассовым состоянием и audit event. Запрет двух пересекающихся смен для одного терминала.
- Статусы: CLOSED/OPEN; закрытие фиксирует endedAt, итог выручки, оплат, возвратов, выдач и отказов.
- После завершения смены показывать подтверждение/итог **30 секунд**, затем полностью блокировать экран и отзывать рабочий доступ (на сервере; фоновые вкладки и старые cookie не должны обходить запрет).
- «Заблокировать» (без окончания смены) скрывает UI и отзывает/приостанавливает авторизацию до повторной MAX-проверки; действующая бизнес-смена может остаться открыта.
- Отсутствие связи во время закрытия: не показывать ложный успех. Серверный факт закрытия, а не localStorage, является источником истины.

## 4. Технологическое меню и стартовая диагностика
- Техменю доступно из блокировки в режиме **только диагностического просмотра** либо в рабочем интерфейсе с правами техника/администратора для опасных действий; обычный продавец не может исполнять тестовую выдачу/калибровку.
- На старте терминала — опрос зарегистрированного оборудования, драйверов и интеграций через локальный агент оборудования; список устройств формируется из конфигурации точки, а не из любого устройства ОС.
- Проверить: дисплей/тачскрин (если есть датчики/драйверы), QR/штрихкод-сканер, чековый принтер (подключение, бумага, ошибка, крышка), кофемашина и фризер (состояние/ошибка/готовность), связь с backend, канал MAX (как серверная проверка), платёжный провайдер, фискализацию, сеть/DNS/TLS, задержку/доступность канала и примерную скорость (при наличии безопасного тестового endpoint).
- Статусы: OK / ПРЕДУПРЕЖДЕНИЕ / КРИТИЧЕСКАЯ ОШИБКА / НЕ НАСТРОЕНО / НЕТ ОТВЕТА. Показать имя устройства, обязательность, время последнего ответа, описание, действие для оператора.
- Не считать устройство ОК только потому, что его драйвер найден: использовать heartbeat/статус периферии. Не выдавать «всё OK», если связь с диагностическим агентом отсутствует.
- При отказе некритичного устройства допускаются только операции, не требующие этого устройства. Пример: принтер без бумаги — предупреждение, но продажи допустимы **лишь если способ фискализации и предоставления чека правомерно работает без печати**. Кофемашина неисправна — блокировать кофе, не обязательно мороженое. Нет подтверждённой оплаты или backend — блокировать оплату и выдачу всех товаров.
- Интерфейс показывает текущий состав/технические характеристики: модель, серийный номер (по роли), прошивки, версия агента, драйвер, интерфейс USB/COM/Network/Bluetooth, состояние и обновления.

## 5. «Клуб Тимоши» на терминале
- **Никаких общих списков клиентов, ФИО, email и телефонов продавцу не показывать.**
- Клиент **сам диктует номер**. Продавец вводит его в поисковое поле. Сервер проверяет актуальную точку, роль, рабочую сессию, rate limit и журналирует обоснованный поиск.
- Если клиент найден и подтверждён: экран только «Участник клуба» и **доступный бонусный баланс**, без ФИО и номера в ответе. Списания бонусов — только по правилам программы и с подтверждением клиента (дополнительное подтверждение при необходимости); один телефон не даёт права списывать чужие бонусы.
- Если клиент отсутствует: «Пригласить в клуб?» → **«Вступить» / «Отказаться»**. Для «Вступить»: покупатель выбирает **MAX или Telegram**. Терминал создаёт одноразовый запрос/deep link для бота, но **не создаёт подтверждённый профиль сразу** и не отправляет спам на произвольный телефон.
- Бот просит покупателя подтвердить владение номером через request_contact, затем представляет политику ПДн и запрашивает отдельное обязательное согласие. Рекламное согласие — независимое и необязательное. Только после подтверждения номера и согласия backend завершает регистрацию и фиксирует тип, версию, время, канал и ID согласия.
- Если отказался — не создавать клиентский аккаунт, не сохранять номер в журнале, не блокировать разовую покупку. При желании допускается гостевая покупка без клуба.
- Уже существующий TerminalChannelChallengeService — канал подтверждения владельца контакта; архитектура требует адаптации для сценария TimoPOS без смешивания с SellerMaxAuthService.
- Не допускать перебора телефонных номеров (поисковый оракул); защита от массовой проверки membership с rate limiting и минимизацией ответа. На неавторизованном терминале никакой поиск по телефону не доступен.

## 6. Неизменяемые требования
- Основной сервер 78.140.15.84; 91.186.217.13 — Telegram-канал.
- Домен app.utimoshi.ru сохранить без redirect.
- Не менять работающий MAX-бот «Soft_ICE Безопасность».
- Оплата через ЮKassa/СБП проверяется сервером, выдача только при SUCCEEDED и разрешении точки/смены/часов.
- Все изменения только в отдельной ветке до интеграционных тестов и одобрения релиза на production.

## 7. Приёмочные тесты
1. 07:59:59 — вход/просмотр доступен, смена/продажа/выдача запрещены.
2. 08:00:00 — начало смены возможно, только после него разрешена продажа.
3. 17:59:59 — продажа разрешена; 18:00:00 — запрет независимо от состояния shift.
4. Смена закрыта: итог 30 сек, затем обязательная блокировка и отзыв сессии; обратный счёт не подменяет backend.
5. Повторное получение MAX-кода отменяет старый; код действителен 5 мин и не может использоваться второй раз.
6. Неисправный принтер с бумагой/без бумаги, сканер отключён, кофемашина недоступна, backend offline: корректное разграничение warning/critical и товаров.
7. Не настроенные устройства обозначены «не настроено», отсутствующие ожидаемые — как ошибки, no false success.
8. Продавец может искать только конкретный диктуемый телефон, не может перечислить клиентскую базу.
9. На найденного клиента — только членство и бонусы, без ПДн; при отсутствии — «Вступить/Отказаться».
10. Запрос регистрации через MAX/Telegram требует подтверждение своего контакта и отдельное обязательное согласие на ПДн; отказ разрешает гостевую покупку.
