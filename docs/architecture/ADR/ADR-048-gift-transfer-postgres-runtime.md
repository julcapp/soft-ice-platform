# ADR-048: Постоянное PostgreSQL-хранилище Gift Transfer Runtime

- Статус: принято
- Дата: 31.08.2026

## Контекст

Модели `GiftTransfer`, `GiftInvitation`, `GiftRecipientClaim`, `GiftRedemption`, `GiftReferralLink` и `NotificationDeliveryAttempt` уже присутствовали в Prisma schema и миграции, но рабочая runtime-композиция использовала `GiftTransferRepository` на основе `Map`. После перезапуска процесса подарки, приглашения, статусы принятия, коды выдачи и попытки уведомлений терялись.

Кроме того, `OrderRepository` использовал статус `GIFT_TRANSFERRED`, отсутствовавший в Prisma enum `OrderStatus`.

## Решение

1. Производственная композиция использует `PrismaGiftTransferRepository`.
2. `GiftTransferRepository` сохраняется только как `IN_MEMORY_TEST` для изолированных модульных тестов.
3. Все чтения и записи Gift Transfer переводятся на асинхронный репозиторный контракт.
4. Связанные изменения transfer/invitation/referral/claim/redemption сохраняются транзакциями Prisma внутри репозитория.
5. Попытки доставки идемпотентны по паре `notificationId + channel`.
6. Пользовательские и административные API ожидают асинхронные чтения и не обращаются к внутренним `Map`.
7. В `OrderStatus` добавляется `GIFT_TRANSFERRED` отдельной миграцией.
8. Секрет приглашения и код выдачи не раскрываются в списках и административных ответах.

## Последствия

- состояние подарка сохраняется после перезапуска backend;
- Bot Core, Mini App и Admin API читают одно состояние PostgreSQL;
- повторная попытка доставки обновляет существующую запись канала;
- миграция обязательна до включения нового runtime в любом окружении;
- реальные Telegram/MAX-отправители по-прежнему подключаются отдельным этапом и не включаются автоматически;
- развёртывание в production этим решением не выполняется.
