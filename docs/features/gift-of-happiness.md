# «Подари стаканчик счастья» — интеграционный контракт v1

Статус: **проект к внедрению, НЕ production-ready**. Основание: существующие `backend/src/modules/gift_transfer`, `backend/src/api/v1/giftTransferRoutes.js`. В рабочую систему и платежи изменения не внесены.

## Единственный источник заказа
Подарок — передача права получения **существующего оплаченного заказа** без создания повторной покупки. Статус оплаты должен быть подтверждён платёжным провайдером и синхронизирован с `Order`. Запрещено создавать право выдачи до `SUCCEEDED`. Одна единица заказа -> одно право физической выдачи. Статус подарка не должен автоматически запускать механизм выдачи.

## Публичная ссылка
Предлагаемый URL после настройки домена и роутинга: `https://utimoshi.ru/g/{opaqueInvitationToken}?src=vk&campaign=happy_cup`. Это **шаблон**, а не работающая ссылка. Маршруты: `/gift` — лендинг покупки/отправки; `/g/:token` — просмотр/принятие. Токен: криптостойкий, хранится только его SHA-256; нельзя класть телефон, orderId, цену и ПДн в URL; токены ограничены сроком действия и одноразовой привязкой. UTM/source сохранять из allowlist и в отдельной сущности acquisition touch, без передачи секретного токена в аналитические сервисы и сторонние рефереры.

## Сценарий дарителя
1. Авторизация, подтверждение собственного телефона, имя (существующий `Customer`, `CustomerIdentity`).
2. Покупка и достоверно подтверждённая оплата в действующем контуре, создание предоплаченного заказа.
3. «Передать подарок» -> телефон получателя E.164, необязательное поздравление, явное подтверждение.
4. Атомарно зарезервировать право выдачи, создать GiftTransfer + Invitation в PostgreSQL; получить ссылку и кнопки «Поделиться» для VK, Telegram, MAX, native share / copy.
5. Статус «Ожидает принятия»; дальнейшее уведомление можно отправлять только по доступному законному каналу.
6. До принятия возможна отмена по действующим правилам; дальнейшее управление — по условиям публичной оферты.

## Сценарий получателя
1. Открывает ссылку независимо от платформы (обычный HTTPS веб-интерфейс, адаптивный и доступный вне мессенджера).
2. Видит безопасное описание подарка без раскрытия чужого номера телефона.
3. Подтверждает телефон, **совпадающий с номером, указанным дарителем**, через доверенный OTP/контакт-провайдер; проверка Telegram/MAX identity сама по себе не подтверждает номер телефона.
4. Для нового пользователя создаётся Customer (имя, верифицированный телефон, источник); для существующего используется прежняя CRM-карточка. Потребовать необходимые согласия на ПДн по применимому правовому основанию; согласие на рекламу и подписка добровольны и не блокируют подарок.
5. Отдельная кнопка «Принять подарок»; только после этого право получения закрепляется за получателем.
6. Выбор доступного аппарата и выпуск короткоживущего одноразового кода / QR непосредственно перед выдачей. Секрет кода не хранить открытым.
7. На терминале валидировать код **на сервере атомарно**, проверить статус оплаты, получателя, аппарат, доступность, время, право выдачи; выполнить безопасный физический процесс через MachineDispenseService. `GIFT_REDEEMED` — только по подтвержденному `COMMAND_SHIPMENT_SUCCESS` (или актуальному согласованному событию успешной выдачи), с защитой от повторов.
8. После выдачи ненавязчивое предложение подключить MAX/Telegram/VK, клуб, отзыв/фото — исключительно по отдельным основаниям и согласиям.

## Состояния
CREATED -> INVITED -> AVAILABLE -> ACCEPTED -> REDEMPTION_READY -> REDEEMED;
также CANCELLED, EXPIRED, RETURNED_TO_SENDER; все переходы должны быть транзакционными и идемпотентными. Уточнить корректное изменение состояния физического Order при `GIFT_TRANSFERRED` (сейчас применяется legacy-схема).

## Схема PostgreSQL
Использовать отдельную миграцию без опасного изменения `Order`:
- gift_transfers(id, order_id UNIQUE, sender_customer_id, recipient_customer_id nullable, recipient_phone_encrypted, recipient_phone_hash indexed, status, expires_at, accepted_at, redeemed_at, cancelled_at, version, created_at, updated_at, source_touch_id)
- gift_invitations(id, gift_transfer_id, token_hash UNIQUE, status, expires_at, claimed_at)
- gift_redemptions(id, gift_transfer_id, code_hash UNIQUE, machine_id, status, expires_at, used_at, dispense_operation_id UNIQUE)
- gift_acquisition_touches(id, gift_transfer_id nullable, customer_id nullable, channel, campaign, referrer, landing_path, occurred_at, session_id; exclude secrets and unnecessary PII)
- gift_delivery_attempts(id, gift_transfer_id, channel, status, provider_ref, created_at, sent_at)
- relevant constraints, indexes, audit trail, consent version reference, retention policy.
No in-memory Map for production rights, tokens, rate limits or retries.

## API (дополнение к существующим `/api/v1/me/...`)
- `GET /api/v1/public/gifts/:token`: минимальная публичная карточка (без PII), rate limit.
- `POST /api/v1/me/prepaid-orders/:id/gift`: проверить phoneVerifiedAt и sender name; recipientPhone; вернуть opaque URL/ID без выдачи физических секретов.
- `POST /api/v1/me/gift-invitations/claim`: authenticated, verified recipient phone.
- `POST /api/v1/me/gifts/:id/accept`: authenticated recipient.
- `POST /api/v1/me/gifts/:id/request-redemption`: authenticated recipient; вернуть код только в защищённой сессии.
- `POST /api/v1/terminal/gift-redemptions/authorize`: machine-authenticated + idempotency + transaction, не публичный.
- `GET /api/v1/admin/gift-transfers/statistics`: scoped RBAC; агрегированная маркетинговая воронка.
Существующие контракты должны быть проверены и расширены, а не продублированы.

## Безопасность и ПДн
Не искать человека через публичную выдачу сведений о телефонных номерах. Не считать номер подтверждённым только потому, что его ввёл даритель. Не отправлять рекламные сообщения по номеру получателя без требуемого согласия. Защитить OTP от перебора, коды выдачи от повторов, данные — шифрованием и маскированием. Все попытки и подтверждения журналировать без открытых токенов. Предусмотреть отзыв согласий, законное хранение обязательных транзакционных документов, сроки удаления по политикам; не удалять финансовые данные автоматически при удалении CRM-профиля.

## Тесты и критерии готовности
- подтверждённый платёж -> единственный gift; платёж не SUCCEEDED -> отказ;
- номер отправителя не подтверждён -> отказ;
- новый получатель -> регистрация/OTP -> accept; прежний -> корректное сопоставление;
- чужой подтверждённый номер -> отказ;
- одноразовый invitation, expired invitation, ошибочный код, code replay, параллельные запросы и перезапуск сервера;
- отмена/истечение/возврат без двойного зачисления;
- успешная выдача vs failure/timeout/retry/дубликат callback;
- VK/Telegram/MAX/веб переходы, src/utm, защита от подмены и утечки referrer;
- необязательный маркетинг и подписка, фиксация версий согласий;
- публикация только после отдельного staging прогона, миграции PostgreSQL, резервного копирования, плана отката и согласования production.

## Текущие обнаруженные проблемы
1. `GiftTransferRepository` хранит подарки и коды в Map.
2. `requestRedemption` возвращает контракт `FOUNDATION_ONLY` без аппаратного исполнения.
3. `createGift` проверяет телефон получателя, но не требует `sender.phoneVerifiedAt` и `sender.name`.
4. Нет публичной landing/preview для подарка.
5. README корня репозитория содержит merge-conflict markers и устаревшие цены; не использовать его как источник текущих тарифов.

**Запрет:** не включать в production, пока не выполнены критерии готовности.
