# Android: привязка служебного смартфона

Дата: 2026-10-06. Согласовано владельцем: одно приложение, один сотрудник, роли мастера/техника с явным переключением; один активный зарегистрированный смартфон сотрудника.

Реализован серверный модуль ServiceDeviceBinding и добавляющая SQL-миграция. Модуль подключён к мобильным маршрутам под выключенным флагом; на рабочем сервере не включён, APK ещё не создан. Текущие веб-сессии не объявляются защищёнными этой привязкой.

ServiceDeviceBinding хранит карточку сотрудника, производителя, модель, версии Android/приложения, публичный EC P-256 ключ, его отпечаток, даты регистрации/отзыва и администратора. Частичные уникальные индексы запрещают две активные привязки одного сотрудника и повторное использование действующего ключа. Привязка относится к человеку, а не к отдельной роли или старому отдельному логину.

Первую привязку подтверждает управляющий администратор с проверкой организации. Смена телефона требует отзыва прежней привязки с причиной и аудитом. Самостоятельная передача пароля не регистрирует второй телефон.

Приложение создаёт закрытый ключ в Android Keystore; сервер хранит только публичную часть. Модель является справочным значением, сообщённым клиентом, и не доказывает идентичность оборудования. Для доказательства обладания ключом сервер выдаёт одноразовый случайный challenge на 60 секунд. Подпись SHA256withECDSA покрывает версию протокола, challengeId и nonce. Проверяются сотрудник, срок, отзыв привязки, подпись и однократное использование. Запросы с другого ключа отклоняются.

Это ограничивает доступ к служебным функциям, а не физическую установку APK. Без проверки Android key attestation сервер не доказывает аппаратное происхождение присланного ключа. APK должен исключить ключи и идентификаторы авторизации из резервного копирования. Потеря ключа при удалении приложения требует административной повторной регистрации.

Оставшаяся интеграция перед выпуском APK: мобильные сессии с bindingId, обязательное доказательство ключа и проверка актуальности привязки на каждом рабочем запросе; серверная выбранная роль и роль фотоотчёта; защищённые маршруты регистрации/отзыва; интерфейс администратора; реальная приёмка миграции и двух Android-устройств. Нельзя включать признак «защищённое устройство» до этой интеграции.

Источник Android: https://developer.android.com/privacy-and-security/keystore


## Мобильные сессии: 2026-10-06

Добавлен ServiceMobileSession и маршруты /api/v1/mobile-service, выключенные по умолчанию (SERVICE_MOBILE_ENABLED=true только после приёмки и миграций). Вход возвращает отдельный неприменимый к веб-API токен. При первичном входе роль не выбрана. Для /role и всех /workspace запросов необходим challenge с доказательством ключа. Challenge связан с ID сессии и SHA256(method + LF + originalUrl + LF + SHA256(точные байты тела)); подпись остаётся по signingPayload из ответа. Заголовки X-Device-Challenge / X-Device-Nonce / X-Device-Signature (подпись DER ECDSA в Base64). Challenge получает параметры method/path/bodyHash. Каждый рабочий запрос расходует новый challenge. Проверки сессии повторно читают активность пользователя, организации, сотрудника, ролей и привязки.

Роль сохраняется в ServiceMobileSession, контекст рабочего запроса содержит только одну активную роль. Отчёт сохраняет actingRole, видимость и продолжение ограничены исходной ролью. Старые веб-отчёты без роли не появляются в мобильном кабинете. Административная регистрация: POST /api/v1/admin/service-devices/:memberId, отзыв: POST /api/v1/admin/service-devices/:bindingId/revoke с reason. Эти маршруты также выключены флагом.

Подготовлена миграция 20261006000300_mobile_service_sessions. На рабочем сервере обе мобильные миграции ещё не применены, флаг не включён. Нужна отдельная PostgreSQL-приёмка и APK с ключом Android Keystore; ограничение не считается работающим на телефоне до этих проверок.
