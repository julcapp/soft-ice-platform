# Единый вход в Клуб У Тимоши с физической точки (пилот)

**Решение:** ровно одна *активная основная* QR/NFC-карточка на одну торговую точку. QR и NFC несут один и тот же неизменяемый HTTPS URL. На карточке не размещать три независимых ссылки на клуб/фото/отзыв; всё это открывается внутри клуба после идентификации.

## Existing system contracts (verified on this branch)
- `Customer`: `name`, `phone`, `phoneVerifiedAt`, `primaryIdentityProvider`, relations to `ClubAccount`, `CustomerIdentity`, `CustomerConsent`; не создавать вторую таблицу покупателей.
- `OrganizationLocation`: существующая бизнес-локация; у неё UUID `id` и принадлежность к `organizationId`. Человекочитаемый номер торговой точки (`001`) должен быть сопоставлен с существующей организационной/терминальной моделью, а не подменять UUID.
- `CustomerConsent`: `customerId`, `documentId`, `consentType`, `isGranted`, `consentedAt`, `sourceChannel`, `decisionId`. Не дублировать механизм согласий; решение о публикации пользовательских фото — самостоятельная проверка и соответствующая фиксация.
- MAX/Telegram onboarding и верификация телефона — переиспользовать существующий серверный протокол.

## Backend module already implemented
`backend/src/modules/clubEntry/ClubEntryTagService.js`:
- `generateTagToken()`: криптографическая генерация 20 символьного публичного идентификатора.
- `canonicalUrl(origin,token)`: строго HTTPS, без параметров и произвольных путей.
- `getOrCreatePrimaryTag`: запрашивает транзакционный `repo.createOrGetPrimary`; сам **не** пишет в БД и не обеспечивает уникальность без реального DB constraint.
- `resolveClubTag`: проверяет ACTIVE и заданный тип, возвращает только связанный pointId и фиксированный `CLUB_ONBOARDING`; не перенаправляет на произвольный адрес из пользовательского ввода.

### Required persistence before deployment
Нужна миграция PostgreSQL после сверки основной модели точки:
- `MarketingTag(id, pointId, kind=CLUB_ENTRY, token UNIQUE, status, createdBy, createdAt, revokedAt, installedAt)`.
- Частичный уникальный индекс: одна ACTIVE `CLUB_ENTRY` метка на точку. История отозванных меток сохраняется.
- Транзакционный адаптер `createOrGetPrimary`, race-safe create и повторные запросы без генерации новых активных меток.
- Журнал действий админа и версионирование макетов карточек.

### Required HTTP integration before deployment
- `GET /go/:token` → резолвер токена → **только внутренний** /club/onboarding + защищённый одноразовый привязанный контекст происхождения (не доверять pointId из браузера).
- Никаких данных клиента в QR URL. Не менять публичную URL-схему без миграции уже выпущенных карточек.
- `GET/POST /admin/points/:pointId/marketing-tag` только по RBAC организации; генерация или сохранение в админке лишь через сервер.
- Домен `utimoshi.ru` и пути `/go` подтверждаются в staging. Иллюстративные `/join`, `/photo` и ранее показанные QR **не печатать**, пока фактический HTTPS endpoint не развёрнут.

## Client flow
1. Прикосновение NFC или QR → единая страница.
2. Для нового пользователя: имя и подтверждённый телефон; необходимая информация об обработке ПДн, отдельное добровольное согласие на рекламу.
3. Привязка к существующему `Customer` только по проверенному номеру и идентичности; не доверять произвольно введённому номеру.
4. Для существующего пользователя — вход в ЛК без повторной регистрации; бонусы, история, фото, отзывы, реферальная программа.
5. Фото: отдельное согласие на публикацию при необходимости, модерация, ограничение антифрода и бонусы после утверждённого события; не обещать автоматически бонус за каждую загрузку.
