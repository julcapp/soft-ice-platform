# Домены и контуры интерфейсов

## Назначение доменов

| Домен | Назначение | Кодовая база и доступ |
|---|---|---|
| `utimoshi.ru` | Публичный сайт | Web frontend |
| `app.utimoshi.ru` | Mini App | Mini App frontend |
| `display.utimoshi.ru` | Терминал/монитор аппарата | Terminal frontend + отдельная аутентификация устройства |
| `admin.utimoshi.ru` | Административная панель | Admin Console + backend RBAC |
| `tehnik.utimoshi.ru` | Рабочее место технического специалиста | Admin Console + `SERVICE_SPECIALIST` |
| `master.utimoshi.ru` | Рабочее место ответственного за аппарат | Admin Console + `MACHINE_RESPONSIBLE` и machine scope |

Фактические DNS-записи, IP-адреса, Nginx-конфигурации и сертификаты проверяются
непосредственно перед развёртыванием и не считаются подтверждёнными только по этому документу.

## Архитектурное решение

`admin`, `tehnik` и `master` используют одну кодовую базу Admin Console.
Поддомен выбирает профиль входа и стартовый маршрут, но не выдаёт полномочия.
Доступные разделы, действия и данные определяются backend RBAC и организационным scope.

Отдельные копии Admin Console для ролей не создаются. Идентификаторы
`TECHNICIAN` и `MASTER` не используются как серверные роли.

`display` остаётся отдельным интерфейсом терминала и использует аутентификацию
устройства, а не административную сессию сотрудника.

Каноническая реализация `display` находится в `frontend/miniapp` и запускается через `?mode=terminal&machineId=<id>`. Отдельные `frontend/terminal` и `terminal.utimoshi.ru` не поддерживаются. Ориентация выбирается CSS/layout правилами одного React-потока.

## Условия публикации

- TLS и security headers проверены;
- маршрутизация не направляет домены на feature-ветки;
- backend отклоняет неподдерживаемые роли и чужой organization/machine scope;
- Mini App domain совпадает с зарегистрированным доменом провайдера;
- локальный и внешний `/health` успешны;
- подготовлен проверенный откат.

## Цели производительности Mini App

| Показатель | Цель |
|---|---:|
| Первый skeleton | ≤ 1 с |
| API TTFB p75 | ≤ 500 мс |
| Холодная загрузка MAX p75 / p95 | ≤ 3 с / ≤ 5 с |
| Тёплая загрузка p75 | ≤ 1,5 с |
| Профиль и баланс p75 | ≤ 800 мс |
| Ответ бота p75 / p95 | ≤ 1 с / ≤ 2 с |
| Начальный JavaScript | желательно ≤ 150 КБ gzip |

Telegram, MAX и обычный браузер измеряются отдельно. Цели изменяются только после
зафиксированных измерений и архитектурного решения.

## Демонстрация для поставщика

`https://display.utimoshi.ru/api/supplier-demo/` — отдельный статический изолированный маршрут. Платежи, выдача, сообщения и сохранение данных недоступны; все переходы — демонстрация. Рабочий `/?machineId=TEST-MACHINE-001` остаётся отдельным сценарием и не становится режимом просмотра. См. `docs/testing/SUPPLIER_DISPLAY_DEMO.md`.


## Отдельный адрес тестового Telegram Mini App — 16.10.2026

Подготовлен `https://bot-test.utimoshi.ru/miniapp/` через действующий Aéza TLS tunnel. До выполнения `sudo python3 /home/julcapp/install-test-miniapp-host.py` адрес не включён, кнопка не переключена.

Nginx отдаёт только тот же preorder-test.html, preorder-test.js, tma.css и проверенную локальную копию SDK. `/api/tma/shared-preorder/` проксируется только на существующий TEST preorder router: подпись TEST-бота, allowlist клиента, проверенная привязка, TEST-MACHINE-001 и подтверждённый тестовый магазин. Остальные пути остаются 404, webhook не меняется. UI, БД и серверные сервисы общие; это разделение адресов и маршрутов, не отдельная staging-БД. Существующие тестовые API на рабочих доменах пока не удаляются.

Установщик требует root для Nginx, проверяет исходные anchors и SHA256 SDK, сохраняет резервную копию, проверяет `nginx -t`, HTTPS, отказ недостоверному initData и недоступность рабочих маршрутов. Кнопка переключается только после проверки адреса; при исключении файлы восстанавливаются. После установки пользователь отправляет новый /start — старые сообщения сохраняют старые ссылки. Тестовый платёж/выдача установщиком не выполняются.
