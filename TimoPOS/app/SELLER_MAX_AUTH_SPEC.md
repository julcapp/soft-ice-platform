# TimoPOS — авторизация продавца через MAX (согласованный сценарий, 2026-11-14)

## Область применения
Основной сервер Soft_ICE: 78.140.15.84. Домен: timopos.utimoshi.ru. Бот — основной «Клуб У Тимоши» в MAX, **не менять** отдельный контур «Soft_ICE Безопасность». Эта спецификация не авторизует клиентов Mini App, вендинговых покупателей или технических операторов.

## Пользовательский сценарий
1. Администратор создаёт точку (pointId, код, название, адрес) и запись сотрудника (sellerId, ФИО, E.164 телефон, role=SELLER, status=ACTIVE, pointAssignments). Сотрудник может иметь несколько назначенных точек, но на терминале доступна только точка из конфигурации устройства.
2. Сотрудник открывает TimoPOS: locked screen -> tap -> поле «Номер телефона» -> «Получить код в MAX».
3. Backend нормализует номер, проверяет активного сотрудника, право доступа к текущей точке, состояние устройства, привязку телефона к проверенному MAX user ID. Для несуществующего/неактивного номера интерфейс отвечает нейтрально (не выдавать сведения о сотрудниках).
4. Если verified MAX identity не существует, **не отправлять код незнакомому MAX-аккаунту**: показать безопасную инструкцию подтверждения собственного номера через бота (verified request_contact / профиль). Использовать challenge/deeplink с неперсональным случайным токеном. После подтверждения телефона проверять связь с сотрудником.
5. При успешной проверке backend создаёт challenge на 5 минут и инициирует отправку уникального случайного 6-значного OTP в **личный** чат MAX-бота. Никогда не выдавать OTP в браузере, API-response, журнале или telemetry. Не считать отправку успешной до подтверждения провайдера/очереди.
6. Сотрудник вводит код. Backend проверяет hash код + nonce + sellerId + pointId + deviceId + challengeId, TTL <=300 секунд, attempts <=5, одноразовое погашение в транзакции. При успехе создаёт secure session с ролями и point scope.
7. GET /seller/me возвращает sanitized {sellerId, fullName, maskedPhone, role, point:{id,code,name}, shift:{id,status}}. UI показывает ФИО и точку; действия «Продажа», «Получить» требуют актуальной смены. Полный телефон только при подтверждённой бизнес-необходимости.
8. «Заблокировать» прекращает право выполнять операции до новой проверки/разблокировки. «Выйти» отзывает серверную сессию. Закрытие/окончание смены — отдельный бизнес-процесс, не путать с выходом.

## Предлагаемые API контракты (не реализованы)
- POST /api/v1/seller-auth/challenge {phone, terminalId}
  ответ: {challengeId, expiresAt, deliveryChannel:'MAX', maskedRecipient} (без OTP, ФИО, sellerId).
- POST /api/v1/seller-auth/verify {challengeId, code, terminalId} -> Set-Cookie HttpOnly Secure SameSite; тело {authenticated:true}.
- GET /api/v1/seller-auth/me -> рабочий контекст.
- POST /api/v1/seller-auth/lock -> серверная блокировка сессии.
- POST /api/v1/seller-auth/logout -> отзыв сессии.

## Обязательные меры
- OTP: криптографический генератор, хеш/HMAC с server-side pepper, TTL 5 мин, single-use, предел ошибок 5/челлендж и rate limit на IP/телефон/терминал; cooldown пересылки 60 сек. Устаревший код недействителен при повторной выдаче. Все проверки в транзакции/атомарном update.
- Хранить токены MAX только на сервере. Проверять подписанные входящие webhook; идентичность verified MAX account и привязанный номер. Не путать клиентский customer с employee.
- Cookies HttpOnly Secure SameSite, CSRF для изменяющих state операций, TLS, server-side session revoke, аудит с маскированием ПДн.
- Связь seller ↔ point отдельной таблицей, права не вычислять из полей браузера. Сотрудник заблокирован или удалён → немедленный отзыв сессий.
- Логи: SELLER_LOGIN_REQUESTED, MAX_OTP_SENT/FAILED, SELLER_LOGIN_SUCCEEDED/FAILED, TERMINAL_LOCKED, SELLER_LOGGED_OUT; timestamps/actor/point/device/correlation, без OTP и полного телефона.
- Политика неактивной сессии и требования повторного подтверждения при смене устройства — перед релизом утвердить отдельно.
- При отсутствии MAX/неподтверждённом номере не давать обход через произвольный SMS или демонстрационный PIN.
- Операции оплаты/выдачи только после серверной проверки продавца, точки, открытой смены и остальных инвариантов.

## Повторное использование исходников
Модуль backend/src/modules/bot_core/TerminalChannelChallengeService.js (в локальной ветке) содержит идеи phone fingerprint, verified MAX identity, challenge TTL (текущий default 10 минут), но относится к DISPLAY_PHONE и CUSTOMER; переписывать его под продавцов напрямую нельзя. Создать SellerAuthChallengeService с TTL строго 5 минут. Интеграция через MAX BotRuntime после технического аудита текущего бота.

## Тестовые сценарии
1. Сотрудник активен, assigned point, verified MAX -> 6-значный OTP -> сессия с seller/point.
2. Номер не найден или seller disabled -> отсутствие раскрытия наличия учётной записи.
3. Номер есть, MAX не привязан -> безопасная регистрация, кода нет.
4. MAX identity неверна или телефон другого лица -> запрет.
5. Неверный OTP, expired 301 sec, повторный OTP, параллельный redeem -> запрет.
6. Без shift -> доступ к панели, но не к checkout/fulfill.
7. Другая точка, другая роль, заблокированный терминал -> 403.
8. Повторная блокировка/logout отзывают server-side доступ.
9. Ретраи и недоступность MAX -> устойчивые статусы без обхода.
10. Отсутствие PII/OTP в логах и ответах.
